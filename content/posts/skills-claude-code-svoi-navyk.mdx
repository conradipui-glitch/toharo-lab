<Answer>
Skill в Claude Code — это папка с файлом `SKILL.md`, где описана процедура: как выполнять определённый тип задач. От файла правил проекта отличается тем, что подгружается не всегда, а только когда задача подходит под описание навыка. Благодаря этому можно держать десятки подробных инструкций, не забивая контекст: агент читает лишь ту, которая нужна сейчас.
</Answer>

Ситуация, знакомая всем, кто работает с агентом на одном проекте дольше месяца. У вас есть процедура — например, порядок выкатки релиза: прогнать тесты, собрать changelog, проставить тег, обновить документацию, отправить уведомление. Вы объясняете её агенту каждый раз заново, потому что в файл правил такое класть жалко: процедура нужна раз в две недели, а контекст занимает постоянно.

Skills решают ровно это.

## Чем отличается от AGENTS.md

Разница в том, когда содержимое попадает в контекст.

| | AGENTS.md | Skill |
| --- | --- | --- |
| Когда загружается | Всегда, всю сессию | Только когда задача подходит |
| Что туда идёт | Правила, действующие постоянно | Процедуры для конкретных ситуаций |
| Объём | Один-два экрана | Сколько нужно, хоть с примерами и скриптами |
| Пример | «Тесты запускаются так» | «Как выкатить релиз» |

Практическое следствие: в файл правил идёт то, что должно влиять на *каждое* действие. В навык — то, что нужно изредка, но подробно. Как устроен сам файл правил, разбирал отдельно: <Post slug="agents-md-pravila-dlya-agentov">AGENTS.md — один файл правил для всех агентов</Post>.

## Как устроен навык

Минимальный навык — это папка с одним файлом:

```
.claude/skills/
  release/
    SKILL.md
```

Внутри `SKILL.md` — frontmatter и текст инструкции:

```markdown
---
name: release
description: Выкатка релиза — прогон тестов, changelog, тег, уведомление. Использовать, когда просят выпустить релиз, зарелизить версию или собрать новый билд для продакшена.
---

# Выкатка релиза

## Перед началом
Убедиться, что ветка `main` и рабочее дерево чистое.

## Шаги

1. Прогнать полный набор тестов: `npm run test:full`
2. Собрать changelog из коммитов с прошлого тега: `npm run changelog`
3. Показать changelog владельцу и дождаться подтверждения
4. Проставить тег: `git tag -a vX.Y.Z -m "..."`
5. Запушить тег: `git push origin vX.Y.Z`
6. Отправить уведомление в канал релизов

## Чего не делать
- Не выпускать релиз при падающих тестах, даже если падение «известное»
- Не проставлять тег до подтверждения changelog
```

Положить папку можно в двух местах:

- `.claude/skills/` в проекте — навык виден только в этом репозитории, коммитится вместе с кодом и работает у всей команды;
- `~/.claude/skills/` — личный навык, доступен во всех проектах.

Проектные навыки предпочтительнее: они версионируются вместе с процедурой, которую описывают.

## Описание решает всё

Самая частая ошибка новичка — вылизать текст инструкции и написать описание в три слова.

Работает это так: агент видит **только `name` и `description` всех доступных навыков**. Тело `SKILL.md` он читает лишь после того, как решит, что навык подходит. Значит описание — единственное, по чему принимается решение.

Плохо:

```yaml
description: Релизы
```

По такому описанию агент не поймёт, когда навык применять. На запрос «выпусти новую версию» он его просто не подхватит.

Хорошо:

```yaml
description: Выкатка релиза — прогон тестов, changelog, тег, уведомление. Использовать, когда просят выпустить релиз, зарелизить версию или собрать новый билд для продакшена.
```

Здесь есть и что навык делает, и формулировки, которыми задачу ставят в реальности.

Правило: **в описании перечислите слова, которыми вы сами просите об этой задаче**. «Зарелизить», «выкатить», «выпустить версию» — все варианты, которые приходят в голову. Это не спам ключевыми словами, а способ дать агенту зацепку.

## Что кладут рядом с SKILL.md

Навык — это папка, поэтому в неё можно положить что угодно и ссылаться из инструкции.

```
.claude/skills/release/
  SKILL.md
  changelog-template.md
  scripts/
    collect-commits.sh
```

Это удобно по той же причине, что и сами навыки: подробности лежат в файлах и читаются только при необходимости. В `SKILL.md` пишете «шаблон в `changelog-template.md`», агент откроет его на нужном шаге, а не будет держать в контексте всё время.

Скрипты рядом с навыком — отдельно полезная штука. Всё, что можно выполнить детерминированно, лучше выполнять кодом: агент вызовет скрипт вместо того, чтобы воспроизводить последовательность команд по памяти. Это частный случай общего принципа — <Post slug="tri-sloya-nadezhnogo-agenta">логика не должна жить в модели</Post>.

## Как написать свой за полчаса

**Возьмите задачу, которую объясняли агенту минимум трижды.** Не выдумывайте навык впрок — он устареет раньше, чем пригодится.

**Запишите шаги так, как объясняли бы новому сотруднику.** Обычным языком, по порядку, с конкретными командами.

**Добавьте раздел «чего не делать».** Обычно это самая ценная часть: там оседают грабли, на которые вы уже наступали.

**Напишите описание.** Что делает + когда применять + слова, которыми задачу формулируют.

**Проверьте.** Начните новую сессию и поставьте задачу своей обычной формулировкой. Агент должен подхватить навык сам, без напоминания. Не подхватил — проблема в описании, а не в инструкции.

## Частые ошибки

**Навык вместо файла правил.** Если инструкция должна действовать всегда — ей место в AGENTS.md. Навык может не подключиться, и это нормально по замыслу.

**Слишком общий навык.** «Работа с бэкендом» — не навык, а раздел документации. Под такое описание попадает половина задач, и агент будет тащить его постоянно. Навык описывает *процедуру*, а не *область*.

**Инструкция без критерия готовности.** Добавьте в конец, как проверить, что всё получилось: какая команда должна пройти, что должно появиться в выводе.

**Копия документации.** Если процедура полностью описана в README, навык не нужен — достаточно ссылки. Ценность навыка в том, чего в документации нет: порядок, обходные пути, предостережения.

## Когда навыки не нужны

Честно говоря, на маленьком проекте они не нужны. Пока процедур две-три и вы работаете один, файла правил достаточно.

Навыки начинают окупаться, когда:

- процедур становится больше пяти и они не помещаются в файл правил;
- в проекте работает несколько человек и процедуру надо передать;
- часть процедур нужна редко, но требует подробностей.

Не стройте библиотеку навыков заранее. Заводите очередной тогда, когда в третий раз объясняете одно и то же.

## Что запомнить

Skill — способ держать подробные инструкции, не платя за них контекстом. Ключевой элемент — описание: оно решает, подключится навык или нет, и вылизанная инструкция с плохим описанием не сработает никогда.

Начните с одной процедуры, которую вы устали объяснять. Остальное нарастёт само.
