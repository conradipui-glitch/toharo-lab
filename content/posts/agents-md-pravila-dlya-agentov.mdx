<Answer>
AGENTS.md — это обычный Markdown-файл в корне репозитория, куда складывают инструкции для ИИ-агентов: команды сборки и тестов, соглашения проекта, запреты. Его читают разные инструменты — Claude Code, Codex, Cursor, Antigravity — поэтому правила пишутся один раз, а не отдельно под каждый. Формат не регламентирован: работает любой связный Markdown, важнее содержание, чем структура.
</Answer>

Проблема, которую решает этот файл, выглядит так. Вы просите агента добавить функцию. Он добавляет — и попутно ставит новую библиотеку, хотя в проекте уже есть своя обёртка. Форматирует по-своему, потому что не знал про конфиг. Правит файл в папке, которая генерируется автоматически, и правка исчезает при следующей сборке.

Ничего из этого агент не мог узнать, читая код. Это знание живёт в голове команды. AGENTS.md — место, куда его выгружают.

## Откуда взялся стандарт

Каждый инструмент начинал со своего файла: у Claude Code был `CLAUDE.md`, у Cursor — `.cursorrules`, у других свои варианты. Когда в одном проекте работают разными агентами, приходилось держать три файла с одним содержанием и следить, чтобы они не разъезжались.

`AGENTS.md` появился как общий знаменатель: простой Markdown в корне, без обязательной схемы. Его подхватили основные инструменты, и сейчас это фактический стандарт. Claude Code по-прежнему читает `CLAUDE.md`, поэтому распространённая практика — держать `AGENTS.md` основным, а `CLAUDE.md` делать его копией или коротким файлом со ссылкой.

Проверить, что именно читает ваш инструмент, стоит в его документации: поддержка меняется от версии к версии.

## Что писать

Работает правило: **в файл идёт то, чего агент не может узнать из кода**. Всё остальное — шум, который разбавляет важное.

### Команды

Самая полезная секция. Агент не должен угадывать, как запустить тесты.

```markdown
## Команды

- Разработка: `npm run dev`
- Тесты: `npm test` (один файл: `npm test -- path/to/file.test.ts`)
- Проверка типов: `npm run typecheck`
- Линтер с автофиксом: `npm run lint -- --fix`
```

Пишите строки, которые можно скопировать. «Запустите тесты» — бесполезно, `npm test -- --watch=false` — полезно.

### Запреты и неочевидные ограничения

То, что взорвётся, если агент не знает.

```markdown
## Не трогать

- `src/generated/` — генерируется из схемы, правки затираются при сборке
- Миграции — только через `npm run db:migrate`, руками SQL не писать
- `legacy/` — код на поддержке, новые фичи туда не добавляем
```

Каждая строка здесь — сэкономленный час разбирательств.

### Соглашения, которых нет в конфигах

Если правило проверяется линтером — не дублируйте его, агент увидит ошибку при запуске. Пишите то, что автоматика не ловит:

```markdown
## Соглашения

- Даты внутри системы — всегда UTC, конвертация только на отображении
- Новые эндпоинты — с версией в пути: `/api/v2/...`
- Ошибки пользователю — по-русски, в логи — по-английски
```

### Как проверить, что готово

Дайте агенту критерий приёмки, иначе он определит его сам.

```markdown
## Перед коммитом

1. `npm run typecheck && npm test`
2. Новый код покрыт тестами
3. Изменения в API отражены в `docs/api.md`
```

## Чего не писать

**Пересказ структуры папок.** Агент прочитает дерево быстрее, чем ваш список, и ваш список устареет первым.

**Общие советы по хорошему коду.** «Пиши читаемо», «избегай дублирования», «следуй SOLID» — модель это знает. Такие строки только разбавляют файл.

**Описание бизнес-логики целиком.** Для этого есть код и документация. В AGENTS.md — только те инварианты, нарушение которых ломает систему.

**История решений.** «Раньше использовали X, потом перешли на Y» — это для ADR или коммитов. В файле правил устаревает и начинает вводить в заблуждение.

## Почему короткий файл работает лучше

Здесь контринтуитивный момент. Кажется, что чем подробнее правила, тем точнее агент следует. На практике наоборот.

Файл правил попадает в контекст целиком и остаётся там всю сессию. У внимания модели есть бюджет: чем больше в контексте текста, тем слабее вес каждой отдельной строки. Двести строк общих рассуждений размывают пять действительно критичных запретов.

Практический ориентир: **файл должен помещаться на один-два экрана**. Если не помещается — половина написанного там лишняя. Подробные процедуры, которые нужны изредка, лучше вынести в <Post slug="skills-claude-code-svoi-navyk">навыки</Post>: они подключаются только когда пригодятся.

Проверка на каждую строку: что сломается, если её удалить? Не можете ответить конкретно — удаляйте.

## Как файл наполняется со временем

Не пытайтесь написать исчерпывающий файл сразу. Работает накопительный подход.

**Правило двух раз.** Поправили агента дважды по одному поводу — это кандидат в AGENTS.md. Один раз — случайность, два — закономерность, которую дешевле записать.

**Удалять так же активно, как добавлять.** Правило про библиотеку, которую выпилили полгода назад, хуже отсутствия правила: агент будет ему следовать.

**Ревизия раз в квартал.** Пройтись по файлу и вычеркнуть всё, что устарело. Занимает десять минут.

## Монорепозиторий

В большом репозитории один файл на корень не работает: правила фронтенда не нужны при работе с бэкендом.

Раскладывайте по пакетам:

```
AGENTS.md                    # общее: как запустить всё, общие запреты
apps/web/AGENTS.md           # правила фронтенда
apps/api/AGENTS.md           # правила бэкенда
packages/ui/AGENTS.md        # правила библиотеки компонентов
```

Большинство инструментов читают ближайший файл вверх по дереву от того места, где идёт работа. В корневом файле держите только то, что верно для всего репозитория.

## Как проверить, что агент действительно читает файл

Простой способ: положите в файл легко проверяемое правило и посмотрите, соблюдается ли оно.

```markdown
## Соглашения

- Сообщения коммитов начинаются с типа в квадратных скобках: `[fix] ...`
```

Попросите агента закоммитить изменение. Если формат совпал — файл прочитан. Если нет — проверьте имя и расположение файла: чаще всего дело в том, что инструмент ждёт его в другом месте.

Второй способ прямее — спросить у агента: «какие правила проекта ты видишь?» Ответ покажет, что именно до него дошло.

## Частые ошибки

**Файл написан для человека, а не для агента.** Красивое введение, история проекта, благодарности. Всё это занимает контекст и не влияет на поведение. Онбординг людей — в README, правила для агента — в AGENTS.md.

**Правила без причины.** «Не используй `any`» агент выполнит формально и напишет `unknown` там, где нужен нормальный тип. «Не используй `any` — мы ловим ошибки типов на сборке, `any` их скрывает» даёт понимание, а не запрет.

**Противоречия.** В одном месте «пиши тесты на всё», в другом «тесты только для публичного API». Агент выберет одно из двух, и не факт что то, которое вы имели в виду.

**Дублирование в CLAUDE.md вручную.** Два файла разъезжаются в первый же месяц. Либо копируйте автоматически, либо в `CLAUDE.md` пишите одну строку: `См. AGENTS.md`.

## Готовый шаблон

Отправная точка, из которой удаляйте лишнее:

```markdown
# Правила проекта

## Команды
- Разработка: `...`
- Тесты: `...`
- Проверка типов: `...`
- Линтер: `...`

## Не трогать
- `путь/` — почему

## Соглашения
- Правило — короткое объяснение зачем

## Перед коммитом
1. Что запустить
2. Что проверить
```

Пять секций, каждая по делу. Если получилось длиннее двух экранов — сокращайте.

## Что запомнить

AGENTS.md стоит примерно двадцать минут работы и окупается на первой же неделе. Главное — держать в нём только то, чего агент не узнает сам, и удалять устаревшее так же охотно, как добавлять новое.

Файл правил — не документация проекта. Это короткая записка человеку, который умеет читать код, но не был на ваших планёрках.
